# ADR-0011：发布策略修订 —— 根目录产物同步

- 状态：已采纳（部分修订 ADR-0007）
- 日期：2026-10-23

## 背景

用户在验收阶段澄清了一个关键事实：

> 线上仓库是 `https://github.com/kkkh/garden-website`，已配置好 git，**推送后就能更新线上网站**。

这推翻了 ADR-0007 中「部署需要人工在平台侧把输出目录改为 `dist`」的假设，同时引入一个 P0 级风险：

| 事实         | v1                                      | v2                                                       |
| ------------ | --------------------------------------- | -------------------------------------------------------- |
| 站点服务位置 | 仓库**根目录**（`index.html` 直接在根） | Astro 构建产物在 `dist/`                                 |
| 仓库根内容   | 可服务的静态站                          | 源码（`src/`、`scripts/`…），**根目录没有 `index.html`** |
| 推送后果     | 线上更新                                | **若平台从根目录服务，则全站 404**                       |

而托管平台（响应头 `Server: edgeone makers`）的「构建命令 / 输出目录」配置无法从代码侧读取，也无法访问其控制台。

## 决策

采用**双兼容发布策略**：构建产物同时存在于 `dist/` 与仓库根目录。

1. 新增 `scripts/sync-root.mjs`：
   - 把 `dist/` 的 13 个顶层条目（4 个 HTML、`_astro/`、`icons/`、`og/`、`beian/`、`.well-known/`、`robots.txt`、`site.webmanifest`、两个 sitemap）同步到仓库根；
   - 用 `.release-manifest.json` 记录同步清单，下次同步时清理已不存在的旧产物（避免残留导致陈旧页面）；
   - `--check` 模式用于门禁：比对根目录与 `dist/` 的文件集合与体积、以及清单一致性。
2. 新增 npm 脚本：
   - `npm run release` = `build` + 同步 + 校验；
   - `npm run check:release` = 仅校验；
   - `verify` 在 `build` 之后插入 `check:release`，**忘记同步就会门禁失败**。
3. 根目录产物纳入版本控制，并在 `.prettierignore`、`eslint.config.mjs` 中排除（它们是压缩/打包输出，不参与格式化与 Lint）。

## 为什么这样做

| 平台可能的配置                                          | 该策略下的行为                                   |
| ------------------------------------------------------- | ------------------------------------------------ |
| 纯静态，服务仓库根目录                                  | 根目录即 v2 产物 → 正常服务 ✅                   |
| 构建型，执行 `npm ci && npm run build`，输出目录 `dist` | 使用构建产物 → 正常服务 ✅                       |
| 构建型，但输出目录被设为仓库根                          | 平台部署快照覆盖，但源仍是构建产物 → 正常服务 ✅ |
| 构建型，命令有误（如未装依赖）                          | 根目录产物作为兜底仍可服务 ✅                    |

即：**在任何一种配置下，「推送 main」都不会导致 404**，因此满足用户「推送即可更新线上」的预期，也不需要用户先做平台侧配置。

## 代价与权衡

| 代价           | 说明                                                                        | 缓解                                                                     |
| -------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 仓库体积增加   | 根目录产物约 31 MB（含 22 张截图与 10 张架构图的 AVIF/WebP/JPG 多尺寸派生） | 已注意到；后续可评估只提交单一格式或以发布分支承载（见下）               |
| 产物与源码同库 | 根目录混有源码与产物                                                        | 用 `.release-manifest.json` 精确界定产物边界；lint/format 排除；文档说明 |
| 需要记住同步   | 改源码后若不同步，根目录仍是旧页面                                          | `verify` 内置 `check:release` 门禁，CI 同样会失败                        |

## 替代方案与否决理由

| 方案                                                  | 否决理由                                                                                                                                 |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 依赖平台构建，直接推送 `dist` 结构（ADR-0007 原方案） | 无法确认平台是否执行构建与输出目录，赌错则全站 404。属于「不可接受的上线风险」                                                           |
| 单独开 `release` 分支只放产物，用户自行在平台切换分支 | 需要用户在平台侧操作，与「推送即更新」的既有工作流不符，且增加出错面                                                                     |
| 让 Astro 直接输出到仓库根（`outDir: '.'`）            | 构建会与源码目录混写（`_astro/` 与 `src/` 同级），且 `astro check`、Git 忽略、编辑器索引都会受影响；同一份产物出现两个位置，反而更难维护 |
| 先推送小改动探测平台行为                              | 探测本身也要经过 main（即生产），风险等同；而双兼容方案已经覆盖所有分支情形                                                              |

## 影响

| 影响面   | 变化                                                                                 |
| -------- | ------------------------------------------------------------------------------------ |
| 发布流程 | 改完源码执行 `npm run release` → `git add` → 提交 → `git push origin main`           |
| 门禁     | `verify` 增加 `check:release`（第 8 步）                                             |
| 文档     | 更新 `docs/operations/deployment.md`、README 部署段；ADR-0007 标注被本 ADR 修订      |
| 回滚     | 不变，仍见 `docs/operations/rollback.md`；且因为根目录始终有可服务文件，回滚粒度更细 |

## 风险与回滚

| 风险                                       | 缓解                                                       | 回滚                                             |
| ------------------------------------------ | ---------------------------------------------------------- | ------------------------------------------------ |
| 根目录产物过期（提交了源码但忘记同步）     | `verify` 与 CI 的 `check:release` 会失败                   | 运行 `npm run release` 后重新提交                |
| 旧产物残留（某次构建文件名变化）           | 清单驱动的清理逻辑 + 校验模式会报「残留旧产物」            | 同上                                             |
| 平台「构建型」构建失败导致回退到根目录产物 | 根目录产物本身可用，站点不会挂                             | 修复构建命令或依赖后重新推送                     |
| 仓库体积继续增长                           | 监控；未来若引入更多图片，考虑把产物迁到发布分支或对象存储 | 删除根目录产物并改回纯 `dist` 部署（需平台确认） |

## 验证

```bash
npm run release                     # 构建 + 同步 + 校验
node scripts/sync-root.mjs --check  # 期望：根目录产物与 dist 一致（437 个文件）

# 用「纯静态根目录」方式模拟平台（关键验证）
python3 -m http.server 8123
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8123/                 # 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8123/privacy.html     # 200
curl -s http://127.0.0.1:8123/ | grep -c 'data-carousel'                        # 2（v2 标记）
```

实测结果：12 条路由全部 200，v2 标记存在（`data-carousel` × 2、`application/ld+json` × 3）。

生产实测（2026-10-23，推送 `main` 后）：

| 观察项                    | 结果                                                                          |
| ------------------------- | ----------------------------------------------------------------------------- |
| 生效时间                  | 推送后约 110 秒（轮询 23 次 × 5s）由 v1 切到 v2                               |
| 服务来源                  | 线上 `index.html` 与仓库根同步产物逐字节一致 → 平台从仓库根服务               |
| 页面与资源                | 4 个页面 200、未知路径 404；manifest/sitemap/OG/图标/备案图/AASA/CSS 全部 200 |
| 浏览器烟测（桌面 + 移动） | Playwright 21 项断言全部通过；0 控制台错误、0 第三方请求                      |
| 证据                      | `docs/acceptance/logs/deployment-verification.txt`                            |

该结果确认了「双兼容」策略的必要性：平台确实按纯静态根目录服务，若仅推送 `dist/` 结构，线上会全站 404。
